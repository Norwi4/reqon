# Сайт Reqon

Готовый сайт для собственного VDS: главная, возможности, загрузки с архивом, документация, история релизов, о проекте и 404. Фирменные изображения, реальные скриншоты и шрифты хранятся локально. Внешние библиотеки для запуска не нужны. Требуется Node.js 22 или новее.

## Развёртывание reqon.ru

Сайт размещён на `168.113.178.77` в `/opt/reqon/website`. Используется установленный Nginx и сервис `reqon-website.service`; Node.js 22.23.4 находится в `/opt/reqon/node`. Приложение работает от системного пользователя `reqon`, слушает только `127.0.0.1:4173` и читает публичные релизы GitHub без токена. Режим на сервере — `RELEASE_SOURCE=github`.

В GitHub опубликованы 22 выпуска с 29 установщиками и файлами `SHA256SUMS.txt`. Последние сборки: Windows 0.13.8, Linux portable 0.13.4, Astra Linux 0.13.2. Скрипт `tools/publish-releases.mjs` проверяет суммы, собирает каждый выпуск в черновике и публикует его после загрузки всех файлов. Предпросмотр — `node website/tools/publish-releases.mjs`; публикация — та же команда с `--publish`. Он использует существующий Git credential helper и не сохраняет учётные данные.

Зона DNS создана через ISPmanager и синхронизирована с `ns1.firstvds.ru` и `ns2.firstvds.ru`: `reqon.ru` и `www.reqon.ru` указывают на `168.113.178.77`. На момент развёртывания публичная делегация ещё использовала NS регистратора. До её обновления сервер доступен по `http://168.113.178.77/`.

Таймер `reqon-https-bootstrap.timer` каждые 10 минут проверяет публичный DNS через два резолвера. Когда домен указывает на этот VDS, он получает сертификат Let's Encrypt через webroot и включает HTTPS с перенаправлением HTTP. Если `www` тоже готов, он включается в сертификат и перенаправляется на основной домен. После настройки обоих имён начальный таймер отключается; продление сертификата обеспечивает `certbot.timer` с проверкой и перезагрузкой Nginx. Скрипт не меняет DNS и не выпускает сертификат, пока DNS не готов.

Диагностика на VDS:

```sh
systemctl status reqon-website --no-pager
journalctl -u reqon-website -n 50 --no-pager
journalctl -u reqon-https-bootstrap -n 30 --no-pager
systemctl list-timers reqon-https-bootstrap.timer certbot.timer
curl -I -H 'Host: reqon.ru' http://127.0.0.1/
```

Конфигурация сайта — `/etc/nginx/conf.d/reqon-site.conf`; описание systemd-сервисов и установка — в `deploy/`. После изменения шаблонов на VDS: `cd /opt/reqon/website && SITE_URL=https://reqon.ru /opt/reqon/node/bin/node src/build.mjs && systemctl restart reqon-website`. При переносе исходников сохраняй права `reqon:reqon` на `.cache/`; остальные файлы доступны сервису только для чтения.

## Локальный запуск

Из корня репозитория:

```powershell
node website/src/build.mjs
node website/server.mjs
```

Открой http://127.0.0.1:4173/. Также можно запустить `website/start-local.cmd` двойным щелчком. Сервер работает, пока открыто его окно; Ctrl+C останавливает его.

Из папки `website` доступны команды:

```text
npm run build
npm start
npm test
```

`npm install` не требуется. Сборщик — `src/build.mjs`, общие элементы — `src/components.mjs`, страницы — `src/pages.mjs` и `src/docs.mjs`, оформление — `public/styles.css`, поведение — `public/app.js`. После изменения шаблонов выполни сборку. Node обслуживает `public/`, API и скачивание; открытие HTML через `file://` не поддерживается.

Дизайн переработан по продуктовому референсу Postman API Client: компактная светлая навигация, тёмный первый экран с интерфейсом Reqon, светлые разделы возможностей и документации. Маскот используется на странице о проекте. Цветовой акцент, логотип и шрифты сохранены из материалов Reqon.

Логотип в шапке и подвале, favicon и Apple Touch Icon взяты из `Reqon_Icon_Pack_Approved`. Это утверждённые растровые изображения; старые SVG из `Reqon_Developer_Icons_v2` на сайте не используются.

Скриншоты `http-current.png` и `grpc-current.png` получены из текущего кода приложения с временной базой и локальными демонстрационными HTTP/gRPC-серверами. Их можно пересоздать командой `python website/tools/capture-product.py` из корня репозитория при установленных зависимостях настольного приложения. Скрипт работает вне экрана, не обращается к пользовательским коллекциям и не меняет данные рабочего приложения. Для самого сайта Python не требуется.

## Как выбираются релизы

По умолчанию включён `RELEASE_SOURCE=hybrid`:

1. Сервер запрашивает опубликованные релизы `Norwi4/reqon` через GitHub REST API и проходит все страницы списка.
2. Исключает черновики, prerelease, RC, beta, nightly, незавершённые и пустые файлы.
3. Добавляет локальные установщики из `../dist` (можно изменить `RELEASES_DIR`).
4. Для одинаковой платформы и версии предпочитает опубликованные файлы GitHub.
5. Для каждой платформы выбирает наибольшую числовую версию, а при равных версиях — самый поздно загруженный файл. Поэтому 0.13.10 новее 0.13.9, а повторная загрузка 0.12.0 не заменяет 0.13.8.

Платформы независимы: Windows, Linux portable и Astra DEB могут иметь разные последние версии. Режим `github` использует только GitHub, `local` — только каталог файлов.

Поддерживаемые имена:

```text
Reqon-Setup-0.13.8-win64.exe
Reqon-0.13.4-linux-x86_64.tar.gz
reqon_0.13.2_astra1.8_amd64.deb
```

Старые имена `Getman-Setup-<версия>-win64.exe` и `getman_<версия>_astra1.8_amd64.deb` распознаются для архива. Файлы без версии, например `Reqon-windows.zip`, не включаются: их нельзя однозначно связать с выпуском. Тестовым файлам назначай суффикс `-beta` / `-rc` или держи их вне каталога релизов.

### Скачивание с GitHub без перехода на его страницу

Кнопка «Скачать» использует `browser_download_url` конкретного файла, например:

```text
https://github.com/Norwi4/reqon/releases/download/v0.13.8/Reqon-Setup-0.13.8-win64.exe
```

Браузер начинает загрузку файла без открытия страницы репозитория. Сайт остаётся на VDS, трафик установщиков обслуживает GitHub. Репозиторий и релизы должны быть публичными для анонимных посетителей. Серверный токен не делает файлы приватного репозитория публично доступными.

Для постоянной ссылки на последнюю сборку доступны:

```text
/download/latest/windows
/download/latest/linux
/download/latest/astra
```

Они возвращают HTTP 302 на текущий файл. Сайт намеренно не полагается на отметку GitHub «Latest»: определяет максимальный номер версии самостоятельно.

### Публикация новой версии

На GitHub создай release с тегом `v0.13.8` (или `0.13.8`), добавь описание и загрузи соответствующие файлы в Assets. Номер в имени файла должен совпадать с тегом. Для стабильного выпуска не включай «Set as a pre-release». Удобнее сначала подготовить draft, прикрепить все файлы и только потом опубликовать его.

Релизы разных платформ можно публиковать под одним тегом, если их версии совпадают. Для текущих разных версий нужны отдельные релизы `v0.13.8`, `v0.13.4`, `v0.13.2`. Не прикрепляй старую Linux-сборку к новому Windows-тегу с другим номером версии.

Для больших архивов GitHub CLI также поддерживает загрузку файлов (`gh release upload`). Этот проект не устанавливает CLI и не публикует релизы сам: доступ к аккаунту в настройку сайта не входит.

GitHub проверяется сервером не чаще одного раза в 5 минут; открытая страница тоже обновляется каждые 5 минут. При переходе на страницу после успешного обновления серверного кэша новая версия видна сразу. Перезапуск сервера вызывает проверку заново. При недоступности GitHub сохраняется последний успешный список (на диске и в памяти), посетителю показывается сообщение; локальные файлы остаются доступны. Новый выпуск без GitHub-доступа может появиться только после восстановления API.

### Локальные файлы на VDS

Скопируй установщик в каталог релизов сначала как `имя-файла.part`, а после завершения загрузки переименуй в окончательное имя. Это предотвращает скачивание неполного файла. Готовые файлы подхватываются при следующем запросе API без перезапуска. Локальная дата — время изменения файла; при переносе с сохранением mtime сохраняется исходная дата сборки. Для новых выпусков указывай новую версию, не перезаписывай старые установщики.

SHA-256 вычисляется по фактическим байтам с кэшированием по размеру и времени изменения; старые соседние `.sha256` не используются как источник истины. Для GitHub берётся поле `digest`; если оно отсутствует, сайт явно сообщает, что сумма недоступна. Локальные загрузки поддерживают HEAD, Content-Length, ETag и Range для докачки. Каталог приложения, базы, ключи и другие файлы проекта сервер не раздаёт.

Описания локальных релизов лежат в `public/notes/windows-<версия>.md` и `public/notes/linux-<версия>.md`. Для нового выпуска добавь описание перед размещением установщика. Описания GitHub берутся из тела release.

## Развёртывание на VDS через Docker Compose

В комплекте Node-контейнер и Caddy с автоматическим HTTPS. Понадобятся домен с A-записью на VDS, открытые TCP-порты 80/443 и установленный Docker с Compose. При существующем веб-сервере используй его reverse proxy вместо второго сервиса Caddy, чтобы не занимать уже используемые порты.

Размести файлы, например, так:

```text
/opt/reqon/
  website/       # эта папка
  dist/          # локальные установщики; может быть пустой для GitHub-only
```

Из `/opt/reqon/website`:

```sh
cp .env.example .env
```

В `.env` задай реальный `DOMAIN`, например `reqon.example.com`, и при необходимости `RELEASES_HOST_DIR`. В режиме `github` каталог локальных файлов может быть пустым; создай его заранее, чтобы Docker не создавал неожиданную папку.

```sh
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

Для проверки:

```sh
curl -I https://YOUR-DOMAIN/
curl https://YOUR-DOMAIN/api/releases
curl -I https://YOUR-DOMAIN/download/latest/windows
```

Node работает от непривилегированного пользователя и доступен только внутри Docker-сети. Caddy выдаёт HTTPS. В именованных volumes сохраняются сертификаты и кэш GitHub. `.env` исключён из Git и Docker build context. Если нужен токен для повышения лимита GitHub API, передавай его только через серверное окружение; не вставляй в HTML/JS. Публичный репозиторий работает без токена.

При изменении домена или контента снова выполни `docker compose up -d --build`. Страницы генерируются при запуске контейнера с правильными canonical/OG URL; `/robots.txt` и `/sitemap.xml` используют тот же домен. Без `SITE_URL` локальный сервер не придумывает production URL.

### Без Docker

Можно запускать Node как systemd-сервис за имеющимся Nginx/Caddy. Укажи `WorkingDirectory=/opt/reqon/website`, `ExecStart=/usr/bin/node server.mjs`, `HOST=127.0.0.1`, `PORT=4173`, `SITE_URL=https://YOUR-DOMAIN`, `RELEASES_DIR=/opt/reqon/dist` и `RELEASE_SOURCE=hybrid`. До запуска выполни `node src/build.mjs` с тем же `SITE_URL`. Создай отдельного системного пользователя с правами чтения релизов и записи в `website/.cache`. Проксируй запросы на `127.0.0.1:4173` и сохраняй заголовок Range.

## Проверки

`npm test` проверяет числовую сортировку версий, разделение платформ, исключение prerelease и draft, приоритет GitHub, пагинацию, работу при сбое API, добавление/удаление/замену локальных файлов, SHA-256, HTTP Range, HEAD, редиректы, 404 и запрет обхода каталогов.

Сайт не загружает сторонние скрипты, аналитику или удалённые шрифты. Данные описания релиза выводятся как текст, без выполнения HTML. Токен GitHub используется только сервером.

Справочники: [GitHub Releases API](https://docs.github.com/en/rest/releases/releases), [прямые ссылки на файлы релизов](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases).
