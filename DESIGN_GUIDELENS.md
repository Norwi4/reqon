# Техническое задание: UI/UX Refinement — Reqon Desktop

## 1. Контекст проекта

Ты работаешь в репозитории **Reqon** — self-hosted API-клиента для разработчиков, функционального аналога Postman.

Приложение поддерживает работу с API, включая HTTP и gRPC, коллекции запросов, окружения, вкладки, редакторы запросов и просмотр ответов.

Твоя задача — провести комплексную доработку существующего интерфейса, чтобы повысить его визуальную аккуратность, консистентность и удобство использования.

Визуальный ориентир — Postman и современные IDE JetBrains, особенно IntelliJ IDEA.

**Важно:** мы не копируем Postman один в один. Мы используем удачные UX-паттерны, сохраняя самостоятельный фирменный стиль Reqon.

Приложение является self-hosted. Не нужно добавлять облачные функции, авторизацию через внешние сервисы, подписки, приглашения или управление облачными командами.

## 2. Порядок работы

Прежде чем вносить изменения:

1. Изучи структуру репозитория и технологический стек.
2. Найди компоненты главного окна, TitleBar, Sidebar, Collection Tree, Request Tabs, Request Editor, Response Panel и Status Bar.
3. Изучи существующие стили, дизайн-токены, компоненты и механизмы темизации.
4. Найди существующие ресурсы бренда Reqon.
5. Проверь реализацию навигации, сохранения запросов и выполнения HTTP/gRPC-вызовов.
6. Определи, какие из описанных ниже улучшений уже реализованы.

Не создавай дублирующие компоненты и не переписывай работающие механизмы без необходимости.

После анализа приступай непосредственно к реализации.

## 3. Единая дизайн-система

Приведи интерфейс к единому визуальному стандарту.

Рекомендуемые цвета тёмной темы:

| Назначение | HEX |
|---|---|
| Основная рабочая область | `#1F1F1F` |
| Панели и навигация | `#252525` |
| Hover и выделенные поверхности | `#2B2B2B` |
| Разделители и границы | `#363636` |
| Фирменный оранжевый | `#FF8319` |
| Основное действие | `#3B82F6` |
| Основной текст | `#F5F7FA` |
| Второстепенный текст | `#AAB2BD` |

Это целевые значения, а не требование безусловно заменить все существующие цвета. Сначала изучи текущие токены и сохрани совместимость с существующими темами.

Правила:

- Используй централизованные дизайн-токены.
- Не разбрасывай HEX-коды по компонентам.
- Оранжевый используй для брендинга, активных состояний и небольших акцентов.
- Синий сохрани для основных действий, например Invoke.
- Цвета HTTP-методов и статусов ответа должны сохранять собственное семантическое значение.
- Не используй яркие градиенты, крупные тени и чрезмерные декоративные эффекты.
- Поддерживай достаточный контраст текста и элементов управления.

## 4. Отступы и плотность интерфейса

Введи согласованную систему отступов:

- Базовый шаг: 4 px.
- Основные интервалы: 4, 8, 12, 16, 24 px.
- Высота строки дерева коллекций: ориентировочно 28–30 px.
- Отступ между уровнями вложенности: 14–16 px.
- Размер компактных иконок: 16 px.
- Размер иконок в основных панелях: 18–20 px.
- Размер иконки бренда в TitleBar: 24 px.
- Интерактивная область небольших кнопок: ориентировочно 32–36 px.

Все размеры интерфейса должны корректно работать при масштабировании ОС.

Не уменьшай элементы настолько, чтобы ухудшить читаемость или доступность.

## 5. Верхняя панель — TitleBar

Текущая навигация содержит:

`Menu | Back | Forward | Home | Workspaces`

Целевой вариант:

`Reqon Logo | Menu | Back | Forward | Home | Workspaces`

Требования:

1. Размести фирменную иконку Reqon в самом левом верхнем углу.
2. Используй упрощённый логотип енота из существующих ресурсов.
3. Размер логотипа — 24×24 px.
4. Сделай иконку кликабельной с переходом на Home.
5. Добавь tooltip `Reqon — Home`.
6. Не добавляй рядом с логотипом крупную надпись Reqon.
7. Сохрани существующую высоту верхней панели.
8. Не нарушай работу системных кнопок окна.
9. Сохрани возможность перетаскивания окна через свободные области TitleBar.
10. Приведи hover и active состояния кнопок к общему стандарту.

Если фирменная иконка уже корректно интегрирована, не создавай вторую.

## 6. Дерево коллекций — Collection Tree

Сделай дерево коллекций более компактным и информативным.

Реализуй:

- Единую высоту строк 28–30 px.
- Согласованные отступы вложенности.
- Чёткое выделение выбранного элемента.
- Ненавязчивый hover.
- Контекстное меню `⋯`, появляющееся при наведении на строку.
- Корректное сокращение длинных названий с многоточием.
- Tooltip с полным названием элемента.
- Цветовые индикаторы HTTP-методов.
- Возможность свернуть все раскрытые узлы.
- Поиск по коллекциям и запросам с подсветкой совпадений.

Если структура данных позволяет без существенной дополнительной нагрузки, добавь счётчик запросов для коллекций.

Не нарушай:

- Drag & Drop.
- Создание и удаление коллекций.
- Переименование.
- Вложенные папки.
- Сохранение структуры.
- Существующие контекстные действия.

## 7. Вкладки запросов — Request Tabs

Унифицируй внешний вид вкладок.

Требования:

- Активная вкладка должна визуально отличаться от остальных.
- Используй оранжевую линию толщиной 2 px для активной вкладки.
- Активный текст должен быть ярче неактивного.
- Приведи горизонтальные отступы к единому стандарту.
- Крестик закрытия показывай при наведении, а на активной вкладке — постоянно.
- Добавь индикатор несохранённых изменений, если он ещё отсутствует.
- Обеспечь корректную работу длинных названий.
- Сохрани горизонтальную прокрутку и переключение между вкладками.
- Не нарушай восстановление открытых вкладок после перезапуска.

Не меняй существующую модель хранения вкладок без необходимости.

## 8. Редактор запросов — Request Editor

Улучши визуальную иерархию редактора.

Требования:

1. Унифицируй оформление вкладок Message, Authorization, Metadata, Service Definition, Settings и других существующих разделов.
2. Используй одинаковые размеры текста, отступы и активные состояния.
3. Приведи таблицы параметров и metadata к единому стилю.
4. Обеспечь корректную подсветку активной строки.
5. Сохрани читаемость JSON, XML и других форматов.
6. Добавь или улучши команду форматирования JSON.
7. Отображай ошибки валидации в редакторе, если архитектура редактора это поддерживает.
8. Сохрани существующую поддержку gRPC и HTTP.

Не меняй сериализацию запросов и работу сетевого слоя.

## 9. Панель ответа — Response Panel

### 9.1. Пустое состояние

Замени примитивное сообщение `Click Invoke to get a response` на полноценное empty state.

Состояние до первого запроса:

**Заголовок:** `Ready to send`

**Описание:** `Send a request to inspect the response`

Добавь небольшую иллюстрацию маскота Reqon, если подходящий ресурс уже существует.

Требования:

- Иллюстрация должна быть компактной.
- Не используй крупные декоративные блоки.
- Контент центрируется внутри области ответа.
- Empty state не должен мешать изменению размеров панели.
- При появлении ответа он полностью заменяется результатом запроса.

### 9.2. Метрики ответа

После выполнения запроса отображай компактную строку:

`Response | Metadata | Trailers        200 OK | 142 ms | 2.4 KB`

Требования:

- Показывай реальный статус запроса.
- Показывай фактическое время выполнения.
- Показывай размер ответа, если он доступен.
- Не используй фиктивные значения.
- Для gRPC отображай корректный gRPC status, а не HTTP 200 по умолчанию.
- Для ошибок используй семантическую цветовую индикацию.
- Если метрика отсутствует, не выдумывай её.
- Не нарушай существующие вкладки ответа и просмотр metadata/trailers.

### 9.3. Ошибки

Создай согласованные состояния для:

- Ошибки соединения.
- Тайм-аута.
- Ошибки DNS.
- Ошибки TLS.
- Недоступности сервиса.
- Некорректного запроса.

Показывай понятное сообщение и технические детали, если они доступны.

Не скрывай исходную диагностическую информацию.

## 10. Разделитель Request / Response

Улучши разделитель между редактором запроса и панелью ответа.

Требования:

- Очевидный hover при наведении.
- Корректный курсор изменения размера.
- Плавная визуальная реакция без тяжёлой анимации.
- Двойной клик для восстановления пропорции 60/40.
- Ограничения минимальной высоты обеих панелей.
- Сохранение текущих пропорций при обычной работе, если это уже поддерживается.
- Отсутствие конфликтов с выделением текста и прокруткой редактора.

## 11. Поиск

Улучши глобальный поиск.

Целевой UX:

- Комбинация `Ctrl+K` для Windows/Linux.
- Комбинация `Cmd+K` для macOS.
- Подсказка комбинации внутри поля поиска.
- Поиск по существующим коллекциям, запросам и доступным локальным сущностям.
- Навигация по результатам с клавиатуры.
- Enter открывает выбранный результат.
- Escape закрывает поиск.

Используй существующую инфраструктуру поиска, если она имеется.

Не создавай параллельный механизм индексирования без необходимости.

## 12. Нижняя строка состояния — Status Bar

Сохрани минималистичный характер нижней панели, но сделай её информативнее.

Возможные элементы:

- Текущий локальный workspace.
- Console.
- Find.
- Состояние локального подключения, если оно имеет смысл для текущего режима.
- Информация о последнем запросе, если полезна и не дублирует панель ответа.

Не добавляй облачные функции и элементы управления подпиской.

Не перегружай строку состояния большим количеством кнопок.

## 13. Фирменный стиль Reqon

Reqon — самостоятельный продукт со своей визуальной идентичностью.

Основные элементы бренда:

- Геометрический енот — логотип приложения.
- Более детализированный енот — маскот для иллюстраций.
- Фирменный оранжевый `#FF8319`.
- Тёмные нейтральные поверхности.
- Минималистичная технологичная эстетика.

Правила:

- Не используй логотип Postman.
- Не копируй его фирменные иллюстрации.
- Не добавляй маскота в каждую панель.
- Используй маскота преимущественно для empty states, ошибок, About и приветственных экранов.
- Для системных иконок используй упрощённый логотип.
- Не генерируй произвольные новые версии маскота, если уже существуют утверждённые ресурсы.

Если в проекте есть `REQON_BRAND_GUIDELINES.md`, используй его как дополнительный источник дизайн-токенов. Для интерфейса десктопного приложения приоритет имеют требования настоящего ТЗ и существующие рабочие UI-паттерны.

## 14. Светлая тема

Проверь существующую поддержку светлой темы.

Если светлая тема уже реализована:

- Обеспечь корректное отображение новых компонентов.
- Не оставляй жёстко заданные цвета тёмной темы.
- Проверь контрастность текста.
- Проверь активные и hover-состояния.
- Проверь изображения маскота.

Если светлая тема отсутствует, не создавай её с нуля в рамках этой задачи. Зафиксируй это как отдельное улучшение.

- Подключать облачные сервисы.

- Ломать обратную совместимость.
- Массово переименовывать файлы вне задачи.

Следуй существующим соглашениям проекта.

## 17. Критерии готовности

Задача считается завершённой, если:

1. Интерфейс стал визуально более компактным и последовательным.
2. Все основные панели используют единую систему отступов.
3. Активные элементы легко различимы.
4. Дерево коллекций удобно для больших и глубоко вложенных структур.
5. Вкладки запросов корректно отображают состояние.
6. Панель ответа имеет качественное пустое состояние.
7. Метрики запроса отображают реальные данные.
8. Ошибки отображаются понятно и технически информативно.
9. Разделитель панелей работает корректно.
10. Глобальный поиск доступен с клавиатуры.
11. Логотип Reqon органично интегрирован в интерфейс.
12. Существующие HTTP/gRPC-функции продолжают работать.
13. Приложение успешно проходит доступные проверки сборки и тестирования.
